Git이 차세대 메이저 버전인 3.0에서 기본 해시 알고리즘을 SHA-1에서 SHA-256으로 전환하려는 계획에 대해, Git 클라이언트 도구 GitButler 팀이 심각한 부작용과 실효성 부족을 정면으로 비판한 글입니다. 

Git의 객체 무결성을 책임지는 해시 함수로 SHA-1을 교체해야 한다는 논의는 꽤 오래전부터 있었습니다. 2017년 구글의 SHA-1 충돌 공격(SHAttered) 시연 이후 보안 우려가 커졌기 때문입니다. 하지만 글쓴이는 현재 Git이 이미 충돌 탐지 알고리즘(SHA-1DC)을 내장해 실질적인 보안 위협을 막아내고 있는 상황에서, 굳이 생태계 전체를 뒤흔들며 SHA-256을 기본값으로 강제할 이유가 없다고 지적합니다.

글이 흥미로운 이유는 단순히 '바꾸지 말자'는 보수적인 주장에 그치지 않고, 전환 과정에서 개발자들이 치러야 할 비용을 현실적으로 계산해 보여주기 때문입니다. 40자리에서 64자리로 늘어나는 커밋 해시는 터미널과 웹 UI 전반의 가독성을 떨어뜨리고, 저장소 크기와 메모리 사용량을 늘립니다. 무엇보다 기존 SHA-1 저장소와 SHA-256 저장소 간의 상호 운용성이 매끄럽지 않아 수많은 CI/CD 파이프라인, 서드파티 도구, 레거시 스크립트가 광범위하게 깨질 위험이 큽니다. 또한 지금 시점에서 굳이 새 해시를 도입해야 한다면 왜 이미 20년이 넘은 SHA-256이어야 하는지, 훨씬 빠르고 유연한 BLAKE3 같은 현대적인 대안을 고려하지 않은 채 십수 년 전 수립된 로드맵에 얽매여 있다는 비판도 설득력을 얻습니다.

매일 사용하는 도구의 근간이 흔들릴 때 발생하는 비용은 생각보다 거대합니다. 보안 스펙의 숫자 하나를 올리는 것보다, 수천만 개발자와 도구가 얽혀 있는 거대 생태계의 연속성을 유지하는 일이 소프트웨어 공학적으로 얼마나 중요한 과제인지 다시금 생각해보게 만듭니다.
